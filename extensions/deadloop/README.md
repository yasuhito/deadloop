# deadloop extension internals

This directory contains the Pi extension implementation for **deadloop**.

Read the root `README.md` for normal setup.

## Local configuration

Normal configuration is read from `~/.pi/agent/deadloop/projects.json`, with this directory's `projects.json` retained only as a local-development fallback. `DEADLOOP_CONFIG` is an internal transport used to pass the already selected path to child automation processes; it is not a supported operator setting.

Do not commit `projects.json`; it contains local paths and rollout choices.

Automations name their driver by filename, so a local `~/.pi/agent/deadloop/projects.json` written before the CommonJS modules moved to `.cts` still carries the old `.ts` driver filenames. Rewrite each `driverFile` to the `.cts` name shipped in `projects.example.json`; the old names are not accepted. The removed front-end prompt and precheck configuration (`promptFile`, `precheckFile`, `precheckTimeoutSeconds`) is a configuration error now: drivers decide every automation action.

When the attempt-record contract changes, finished attempts keep journals written under the old contract, and the current reader rejects a value they hold. A record whose `phase` is terminal (`github_persisted`, `workspace_closed`, `abandoned`, `authority_released`) is evidence of a finished attempt, not live state, so deadloop treats the contract violation as an *unreadable terminal record* instead of a crash: the host's retained-attempt sweep and the PR work-authority reconciler report it once to the host activity log (`unreadable_attempt_record`) and skip it, `/deadloop-doctor` lists it as `malformed_journal` with the record path, the failing field, its value, and the archive command, and drivers that scan journals skip it. Records at a living phase still fail closed. After review, archive the run directory — do not rewrite the journal:

```bash
mv ~/.pi/agent/deadloop/runs/<uuid> ~/.pi/agent/deadloop/manual-review-archive/
```

`deadloop.json` is an optional shared policy and `projects.json` is an optional local override; neither enables scheduling. `/deadloop-enable` is a fast control-plane operation (ADR 0028): it resolves the required-verification contract from explicit overrides or the built-in `npm run check` default without executing it, then persists enablement and returns. It does not create a verification worktree, run the repository's verification command, or prove repository tests green. The command records execution permission in `~/.pi/agent/deadloop/enabled-projects.json` only after project configuration, trusted base resolution, primary checkout status, repository identity, GitHub authentication, authenticated login, write permission, runtime compatibility, nonblocking lock capability, and missing-label creation succeed. A failed preflight leaves enablement false and starts no background job. When a deterministic host operation itself fails with observed `ENOSPC` or `EDQUOT`, the stop stays local: no execution permission is recorded, no Issue, PR, or agent workflow label changes, the result names the capacity stop, and a small evidence file (`enablement-storage-exhaustion.json`) is recorded for `/deadloop-doctor` until the next successful enablement clears it. Subprocess stderr and pane text alone never classify that cause. Every produced revision is still gated by required verification before push, handoff, or merge. The normalized authenticated login is persisted as an explicit authorized automation identity and overlaid onto runtime `automationLogins`; optional local `automationLogins` may add only other fleet identities whose GitHub login and operator control have been verified. The public example leaves this list empty. Each project overlays inferred or explicit local config, trusted base-branch repo policy, and package defaults. `/deadloop-doctor` reports retained attempt artifacts through the general project-check findings; it no longer looks for enablement-verification worktrees, because none are created. `/deadloop-disable` removes only that permission and lets running agents finish their promise reports. The repo policy file is `deadloop.json`. Repo policy is read only from the trusted `baseBranch` after `git fetch`, never from the PR branch being reviewed.

## Host lock requirement

The supported host is currently a Unix-like platform with a compatible `flock` executable, normally provided by util-linux. The implementation requires nonblocking file-descriptor locks. `/deadloop-enable` exercises that exact capability before persisting enablement, mutating GitHub labels, or starting the scheduler; scheduler startup retains its fail-fast lock check. There is no portable fallback backend yet.

## State

Runtime state and locks live under `~/.pi/agent/deadloop/`. The Automation host holds a GitHub-repository-ID-scoped OS file lock for its full repository-serving lifetime; the kernel releases it when the process exits. Per-launch prompts, promise reports, and atomic attempt journals live under `~/.pi/agent/deadloop/runs/<uuid>/`, outside target worktrees. New writers emit only strongly bound V1 reports; only strongly-bound V1 completion reports are supported. Every V1 report must carry a non-empty three-sentence `summary` beside its identity, and every role prompt states that requirement in its report template; a terminal stop caused by an invalid report names the rejected field (taken from the completion-report validator's message) in the published comment.

GitHub holds the workflow state itself: Issue / PR state, head, labels, comments, and checks. The attempt journal is evidence for monitoring and recovery, never a second state store or permission to act. Request labels (`agent:explore`, `agent:implement`, `agent:review`, `agent:update-branch`) are one-shot labeled events consumed by targeted removal; `agent:in-progress` and `agent:blocked` are the only current-state labels; retry means re-adding a request label. `/deadloop-enable` creates any missing standard labels, and the set matches the Sandcastle-compatible vocabulary: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human` (Issue triage only), `wontfix`, plus the request and current-state labels above.

The host activity log (`~/.pi/agent/deadloop/host-log.jsonl`) records each tick's judgment observationally — tick starts, per-automation results with driver actions, launched attempts with their role, journal reconciliation start/finish with attempt id and duration, model-wait transitions, automations deferred because a retained monitor handoff is still active (`automation_deferred`), due-but-unselected automations (`automation_starved`), unreadable terminal attempt records, enablement writes — as one JSON object per line. An enablement write (and its log line) happens only when the persisted enablement state actually changes; tick-time updates that re-derive an unchanged state write nothing. Appending never gates scheduling: failures land in `host-log-errors.jsonl` only. Tail it with `/deadloop-hostlog [N]` (default 20) or read it with `jq`; see the README's "Host activity log" section for details.

One host serves one repository at a time through that file lock, but several machines or identities may share the same repository: each host reads the same public timeline — an `agent:in-progress` addition authored by any identity listed in the project's authorized automation logins — and reaches the same conclusion about which work is in motion, without claim comments or server-time expiry arithmetic. Whether a running attempt is still alive is answered by the execution runtime alone, and destructive mutations are guarded by compare-and-swap on the exact head. A host whose observation loses touches nothing. Stopped or failed attempts land on `agent:blocked`; resuming always requires a new Agent request. See [ADR 0020](../../docs/adr/0020-stop-proving-work-authority.md) and [ADR 0032](../../docs/adr/0032-github-is-the-workflow-state-source-of-truth.md).

The Automation host fixes the deadloop checkout commit as its loaded code identity. Before any shared enablement write and before each tick can select an automation, it compares that value with the currently deployed checkout commit. A mismatch at the start of a tick asks the session to run `/deadloop-reload` (once per deployed commit, only while the session is idle) so the host continues on the deployed code; a mismatch that a reload did not resolve stops those paths without stopping active attempts, and `/deadloop-status` and `/deadloop-doctor` remain readable with both identities plus the `/deadloop-reload` recovery step (ADR 0035). Uncommitted changes are not observed, and the host never advances its own checkout. The shared enablement state records the last writer's code identity as a required field, for diagnosis only: it never gates reads or writes, and `/deadloop-doctor` reports it so an operator can tell which code generation last wrote shared state. The enablement lock's `.pending` temp files disappear in the same acquisition that creates them; if a process dies mid-acquisition, the next lock acquisition verifies each leftover's owner process and removes the dead ones, and `/deadloop-doctor` reports the residual count.

Automation runs from read-only code snapshots under `~/.pi/agent/deadloop/code-snapshots/<commit>/`, one per code generation; dependencies are fixed by lock-file content hash and hard-linked across generations (ADR 0017). Old generations are never removed automatically because no single session can know whether another session still runs one. `/deadloop-doctor` reports the generation count and capacity of the snapshot inventory, suggests cleanup commands for generations that no trace in shared state names, and leaves removal to a person who has verified no attempt uses them. The deterministic completion of a retained attempt (required verification, push, PR, persistence, workspace closure) runs from the code generation the host currently loads, not from the attempt's launch-time snapshot, so a deployed fix reaches attempts that were already retained at the next tick (ADR 0036); the agent's own run and the recorded `automationDir` stay on the launch-time snapshot.

An Issue implementation request is the latest active GitHub `agent:implement` generation; `ready-for-agent` is optional triage metadata. Before Worker launch, deadloop durably prepares the attempt, deletes only the selected request label, verifies the resulting timeline, records consumption, and only then adds `agent:in-progress`. Cancellation, a raced generation, or ambiguous consumption never launches a Worker.

A new PR request is the latest configured Agent label event for its role. Dispatch binds consumption to that event id, adds `agent:in-progress` without replacing unrelated labels, and individually removes only managed labels present at the baseline. Removing the selected request label is the final step and counts as consumption only after GitHub returns the documented HTTP 200 response. Every planned consumption mutation is surrounded by exact target, repository identity, request-event, and live-label observations. A newer request that is distinguishably live remains available for a later cycle. An absent or ambiguous generation is never guessed back into existence: consumption fails closed with `agent:in-progress` and its prepared attempt evidence still visible. Reviewer and branch-update attempt journals store only the selected request event id; no machine-readable marker comment is posted or read.

Before candidate selection, reconciliation compares `agent:in-progress`, retained attempt journals, and Herdr liveness. The execution runtime alone answers whether an attempt is still running. Missing, runtime-unreachable, stopped, and ambiguous states become a visible idempotent `agent:blocked` recovery state. When this pull request's own attempts recorded why their launches failed before any agent started, the block names those recorded reasons instead of a missing journal, publishes them once per head-and-cutoff generation, and scrubs local filesystem paths from the published text. When deadloop's own deterministic writes or a bound completion report actually observed `ENOSPC` or `EDQUOT`, the block names storage exhaustion with free-capacity recovery steps instead of an unknown cause; the same holds for a stopped reviewer whose completion-report file itself could not be read because of that exhaustion, while pane output alone still names nothing and a termination without any completion report stays a generic technical failure. A strictly later request event can be exposed after a stopped attempt is closed. Attempt journals and finalizer receipts remain evidence, not permission to act.

A settled retention still owns its workspace until something closes it (#395). When a monitor handoff settles - the journal already released the attempt, or the monitored pull request closed - the host closes the still-open workspace with the same ownership proof the completion chain uses, records the outcome in `settled-workspace-cleanup.json` beside the journal, and logs a failed close in the host activity log. The journal scan attempts that closure exactly once for an `authority_released` journal that still owns an open workspace; a `github_persisted` journal keeps its closure in the completion chain, which retries every tick until the workspace is absent. When the runtime no longer lists that workspace, the PR work-authority reconciler releases the journal as finished evidence instead of blocking the pull request (#420). After a failed attempt, `/deadloop-doctor` presents the closure command on its `cleanup_pending` finding.

An Issue Worker whose monitoring handoff disappeared is collected by the same journal scan through `reconcile-report-received-attempt.cts`, whether its journal sits at `agent_started` (a launch whose driver result was lost, #386) or at `report_received`. It observes the shared attemptMonitoring vocabulary: while the runtime reports `working`, `ambiguous`, or `unreachable` the attempt stays retained; with a bound completion report it re-runs the ordinary guarded chain (required verification, destination-bound push, draft PR, persistence, closure); when the report no longer proves its binding it posts one reasoned `agent:blocked` stop with recovery steps and releases the journal authority as `terminal_missing_report`, never rewriting the retained branch or record as success. A record whose target Issue or pull request closed, or whose worktree entity is gone, can never be reconciled (#393): the host judges that once, records a terminal `reconcile-retired.json` marker in the journal, and never reads the record as a reconcile target again. Each reconciliation launch is wrapped by `reconcile_started` / `reconcile_finished` host-log events carrying the attempt id and the lock-holding duration in milliseconds; a retirement is logged as one `reconcile_finished` with result `reconcile_retired`. `/deadloop-doctor` reports a retired record as `cleanup_pending` and offers exactly one archive command (`mv <runDir> <stateDir>/manual-review-archive/`).

Launch and monitoring handoff are never separated by a lost driver result. Immediately after a Worker or explorer launch succeeds, the coordinator driver writes the exact monitor handoff it is about to return into `monitor-handoff.json` beside the attempt journal. The runner consumes that sidecar when it registers the handoff from the driver result; when the driver outcome arrives invalid instead (`driver_invalid_result`, unreadable JSON, or a driver error), the runner re-adopts the sidecar into `pendingDriverHandoff` in the same tick, so the next tick monitors the launched attempt. A driver failure names what was invalid in both `lastError` and the host-log reason, and `/deadloop-doctor` shows the deterministic recovery command for a Worker whose completed report no pending handoff monitors.

A `agent:blocked` pull request whose later Agent request follows the newest blocked event on it becomes a review candidate again, whoever applied that block and whether or not deadloop also explained it in a comment. A request GitHub timestamps no later than the block belongs to the block rather than to the recovery, so a request a person left in place before a stop does not restart it. Most stops deadloop decides clear every request label. A required-verification review stop deliberately keeps `agent:review` as target identity, but its event predates the block and therefore cannot restart the PR. Selection and every launch revalidation read the candidate through the same recovery view, so the exact-target comparison still stops a changed revision, state, draft state, or unrelated label, and a pull request that stops qualifying for recovery keeps `agent:blocked` on the live side and fails the comparison. The driver defers a blocked pull request carrying a request instead of skipping it; a gate that decided this from label text alone would close the recovery route before the recovery view could be built.

Immediately before an automation starts, the host provisions its code snapshot under `~/.pi/agent/deadloop/code-snapshots/` and `dependency-snapshots/`. Code is archived from the host's loaded commit, so uncommitted working-tree changes are excluded; dependencies are copied from the local installation with hard links, keyed by the committed lock-file SHA-256, without running an installer or using the network. A code snapshot is reused for the same commit, and one dependency snapshot is shared across every commit with identical lock content. Hard links share their inode with the package checkout, so only the dependency snapshot's own directories become read-only: the snapshot refuses added, removed, or replaced entries while the checkout stays writable for a later install. Driver paths all use this fixed supply; provisioning failure stops before any mutation-capable driver.

Worker and remaining role-specific monitor prompts run the configured project check through `run-project-check.ts`. The wrapper temporarily isolates the untracked agent scratch areas — `.pi/subagents`, `.pi/npm`, and `.pi/git` — from recursive project tooling, then attempts to restore them after success, failure, timeout, or interruption. If restoration fails, it retains the quarantine and temporary worktree, records both paths, and exposes them through `/deadloop-doctor`. Tracked project files are never hidden; if a scratch area contains a tracked file, validation fails closed instead.

A Worker or reviewer attempt stores its resolved required-verification contract in `attempt.json` before consuming its GitHub Agent request and keeps a host-persisted launch snapshot outside that attempt's run directory. Worker completion runs the fixed contract against the reported output commit; reviewer approval runs it against the fixed PR head. Both write authoritative records outside the worktree. Worker write gates and reviewer approval, successful human handoff, and merge gates reject missing, failed, mismatched, empty, or stale-policy evidence, while `changes_requested` and `human_required` remain reportable without success. Agent-reported additional validations remain non-authoritative evidence. These gates assume an instruction-following but fallible Worker; same-user hostile-process containment requires execution-runtime isolation that the Pi + Herdr support path does not currently provide. See [ADR 0015](../../docs/adr/0015-worker-trust-boundary.md).

A failed Worker-completion record is kept instead of rerun: while its binding (repository, target commit, command, source, base revision) is unchanged, later ticks skip re-execution, and the host posts one fingerprint-marked, idempotent Issue comment containing the exit code and log tail. Only a host-authenticated failed record (provenance in the host evidence directory) qualifies; any binding change, a passed record, or an unauthenticated record triggers a fresh fixed-command run that replaces the record.

## Commands

```text
/deadloop-enable
/deadloop-disable
/deadloop-run-once
/deadloop-status
/deadloop-doctor
/deadloop-abandon-attempt <attempt-id>
/deadloop-hostlog [N]
```

`/deadloop-run-once` runs exactly one normal scheduler tick while persisted enablement is off. It takes the same repository-ID-scoped nonblocking lock as the continuous scheduler, issues a scoped execution authorization in `~/.pi/agent/deadloop/one-shot-execution.json` (never persisted enablement), invokes the shared tick interface with the same policy and side effects, and removes the authorization when the tick finishes. No successor timer is registered and the repository stays disabled. The report distinguishes no-op ticks from reconciled, launched, waiting (model availability, no scheduled retry), and failed ticks.

## Deterministic drivers

Each automation defines a `driverFile`. The driver runs with `DEADLOOP_*` environment variables and returns JSON with `action` values `skip`, `done`, `monitor`, or `error`. `skip` is also the early exit for a candidate-free tick — no cleanup candidates and no candidate Issue or PR — so a tick with nothing to do starts no attempt. `monitor` registers model-free attempt monitoring; no driver action sends a prompt through the Automation host model.

- `issue-coordinator-driver.cts` handles cleanup, candidate selection gates, Issue request consumption, explorer or Worker launch, recovery that reopens a formally stopped Worker's preserved checkout (including after a required-verification stop) for a fresh request, and bounded monitor handoff. Explorer and Worker attempts register deterministic monitoring after launch: a valid completion report enters the shared deterministic completion handler (`complete-deterministic-issue-attempt.cts`), which runs required verification, the destination-bound push, draft PR creation with review request, and attempt persistence for Workers, and persists the bound exploration result plus next Issue action for explorers. A Worker's blocked report becomes a deadloop-authored stop — blocked label, cleared requests, idempotent recovery comment — before its disposable workspace closes.
- `pr-reviewer-driver.cts` consumes one GitHub Agent request per cycle in the order `agent:update-branch`, `agent:implement`, `agent:review`, and handles no-op, pending CI, external review gates, branch-update requests including obsolete ones, one-attempt merge-conflict recovery, reviewer launch, review-repair launch (it consumes the `agent:implement` request, revalidates the persisted findings contract and worktree safety, then starts the repair worker — ADR 0032), and deterministic attempt monitoring without an Automation-host model. Reviewer launch records a complete paginated PR history revision outside the worktree; result dispatch and automatic merge re-observe it and request a fresh review when any commit, diff, comment, submitted review, inline comment, head, or base observation is stale.
- `pr-review-repair-dispatch.cts` consumes completed reviewer outcomes. A review is approved only with no required findings, although it may retain advisory observations. New required findings queue an `agent:implement` repair request only when the reviewer reports that no prior required finding existed or every prior required finding is resolved; persisted, regressed, or mixed prior findings are handed to a human. The dispatcher never launches a worker: it records the review result first, then replaces `agent:in-progress` with the request (ADR 0032). When the request transition finds the PR no longer holding the active claim, it returns without touching GitHub state, and the result carries the grounding it observed (PR state, head match, labels), which reaches the host-log reason through the deterministic completion result (#404). Technical reviewer failures retry once for the exact head — except a blocked report naming an observed `ENOSPC` or `EDQUOT`, which stops immediately without spending that retry. When required verification stops dispatch, actionable findings remain recorded but no repair launches, an empty-finding result is not approved, `agent:review` remains as the review target, and `agent:in-progress` is replaced by `agent:blocked`; the fingerprinted recovery comment is idempotent, and doctor exposes a new-event requeue command only after required verification resolves. A human-required outcome is a completed review: its result is recorded, a draft becomes ready, and every agent workflow label is removed, so the pull request waits on a person and on no agent request.
  - Retry baseline: when a replayed dispatch finds the accepted history observation (`pr-review-history-accepted.json`) and that observation provably is the launch-time history advanced by exactly this attempt's saved result comment — proven by the review-result marker (head, outcome, fingerprint), the attempt persistence marker, and the automation login — and the live GitHub history still matches it, the dispatcher resumes from the accepted checkpoint instead of judging its own result comment a history change. Any later external change (comment, edit, deletion, submitted review, inline comment, head, base, diff) keeps the stale release; an unprovable checkpoint fails closed to the original baseline. `pr-review-result-checkpoint.cts` holds that proof.
- `pr-review-repair-finalize.cts` is the repair worker's only push path. It applies no cumulative repair-count or changed-file-count limit. It runs required verification for every repair, requires an authenticated passed record bound to the fixed attempt contract and repair commit, and reuses only an exact match, then conditionally updates the verified selected branch only while its head equals the validated commit, binding its push to the verified head with an expected-object-ID lease. Required-verification failure or a stale, rewound, or deleted head prevents push. It writes a finalizer receipt outside the worktree.
- `pr-review-comments.cts` renders idempotent, human-readable review and repair-result comments without visible finding IDs. Posted comments are append-only chronological evidence and are never edited. Comment and review bodies are untrusted evidence, not instructions or authority to weaken safety controls. `pr-review-repair-complete.cts` posts repair success only when the structured worker promise, finalizer receipt, and live new head agree. Successful completion replaces `agent:in-progress` with a fresh `agent:review`; the next selection records `repair_rereview`.
- `merge-reviewed-pr.cts` accepts only a validated reviewer approval bound to the expected head, then immediately re-fetches the PR and requires confirmed clean mergeability plus healthy CI evidence before its head-guarded mutation. Missing checks are non-failure, pending waits, unknown stops; failed checks merge only on a fresh CI fallback record bound to the exact head/base/tree/command/policy, and that authorization is posted as a truthful CI fallback note — never as CI success.
- `run-ci-equivalent-verification.cts` executes the repository's complete CI-equivalent command (explicit trusted-base `ciEquivalentCommand`, or the npm convention `npm ci && npm run check`) against the prospective merge tree built with `git merge-tree --write-tree`, or against the fixed base for diagnosis. It pushes nothing: the temporary tree exists only inside a detached worktree under the state directory, and every execution persists its record outside any worktree bound to repository, PR, head, base, tree, command, derivation, policy source, and policy base revision.
- `ci-fallback-gate.cts` observes checks and decides one merge attempt per ADR 0030: absent proceeds, pending waits, unknown stops, terminal failure verifies. On fallback failure it diagnoses the fixed base; a failing base writes a blocking record that suppresses every driver launch without consuming Agent requests until base or contract changes (`src/ci-base-blocking.cts` evaluates currency in status and doctor), while a healthy base allows exactly one repair per episode through the existing review-repair request path — tracked by a head-independent episode identity that only a later human Agent request resets.
- A merge conflict found during review consumes the review request and adds `agent:update-branch`. A later cycle consumes that request and launches the branch-update worker; `pr-branch-update-complete.cts` turns its pushed head into a fresh `agent:review` request, and a request that is no longer needed is consumed with an explanation instead. External-review mutations remain unavailable even when `externalReview` is enabled. The branch-update finalizer defines exact-head, normal-merge, and required-verification safety, and binds its push to the verified head with `--force-with-lease=refs/heads/<branch>:<verified head>`: this expected-object-ID lease is the only force variant deadloop permits, it is permitted only because the candidate is already proved to contain the verified head, a lease mismatch stops the push and reports `stale_head`, and force without a lease stays prohibited.
- `src/ci-review-policy.cts` keeps deterministic check/fallback/repair decisions out of prompts as a pure seam; `src/ci-equivalent-contract.cts` resolves the one trusted-base contract.

## Runner boundary

v0 requires stable Herdr 0.8.0 or newer. The host checks the client and server versions at startup and before every tick, before candidate selection or a mutation-capable driver.

Each Worker, reviewer, review-repair, or branch-update attempt uses one fresh workspace with the worktree's first tab and root pane. The launcher starts the configured agent directly in that root pane; it never creates a tab, splits a pane, replaces a same-name agent, or reuses a terminal. If that new root pane returns the exact structured `agent_pane_busy` pre-start error while its shell is still initializing, the runner retries the identical request every 100 ms within a 5-second monotonic grace period; each request has a 35-second wrapper timeout, and all other or persistent failures retain the workspace. A launch that fails before its agent starts cleans up what it created: it closes the fresh workspace it opened and, when the launch was going to create the checkout, removes that worktree and deletes that branch before the journal records `launch_failed`. What the launch did not create — an opened pull-request checkout, its branch, or a workspace another attempt owns — is never touched, and a launch whose start command already ran keeps its runtime state for the abandonment or reconciliation path. Successful strongly bound attempts close only their workspace after role-specific GitHub persistence, while the linked worktree remains until the existing merged/closed-PR cleanup gate. Blocked, malformed, launch-failed, and ambiguous attempts remain visible and suppress another launch on the same checkout unless deterministic reconciliation proves a stopped owned workspace can be closed while retaining its evidence. A launch-failed journal is never evidence that blocks a newer Agent request: when a request event is newer than the recorded failure, reconciliation releases the failed claim, closes what the runtime proves stopped, and lets the next launch attempt the request. When a fresh Issue request finds a same-name branch or worktree left behind without a stopped journal, the launcher picks the next free suffixed branch name (`-1`, `-2`, ...) instead of failing against the leftover. For a Worker stopped by required verification, the completion gate closes the workspace only after re-reading the Issue and confirming the exact durable stop — the fingerprint comment together with the ready/blocked label state — as its persistence proof.

Each scheduler tick observes at most one retained monitor handoff — round-robin from the least-recently-advanced entry — and then still selects a due automation, so a running Worker never keeps a due reviewer from launching (#402). Issue implementation Workers, explorers, PR reviewers, review-repair workers, and branch-update attempts register deterministic monitoring after launch. Each scheduler tick reads the bound attempt journal, completion report, Herdr turn state, persisted active-work accounting, and configured limit. A working runtime stays active even with quiet output; a valid report enters its role-specific deterministic handler; 24 hours of active work times out; and ambiguous runtime evidence is preserved. No monitor prompt for these roles is sent through the Automation host. A terminal turn without a valid report enters the recognized model-availability wait or the safe stop and is never nudged through conversation. The safe stop binds its hidden marker to the attempt, the selection-time head — plus the selected base for a branch update — and the reason, so reprocessing never duplicates it; a stopped repair relaunches from a fresh `agent:implement` request and a stopped update from a fresh `agent:update-branch` request only when the retained journal proves the same contract and no agent occupies the old workspace.

A later `agent:update-branch` request may adopt commits retained from a blocked branch-update attempt only when the request follows `agent:blocked`, a released attempt carries a valid bound blocked report for the same repository, PR, branch, remote head, and canonical worktree, and the checkout is clean at one exact descendant commit. The launcher receives that commit explicitly and independently proves both its identity and ancestry; every unproven divergent checkout still stops without moving or discarding it.

`/deadloop-doctor` reports version, retention, and cleanup-pending findings without closing anything. For a Worker or reviewer `launch_failed` attempt, it prints `/deadloop-abandon-attempt <attempt-id>` only when the unchanged target, clean input revision, one owned disposable workspace, retained linked worktree, and absence of an agent in the recorded pane are all proven. That explicit operation holds the enablement lock, re-proves the same facts, closes only the attempt workspace, records the terminal `abandoned` evidence in the original journal, preserves the linked worktree, and then requeues the Issue or PR. Immediately before closing, the operation writes a bound `workspace_close_started` receipt beside the original journal. A retry after an interrupted close may continue only when that receipt matches and the recorded workspace and every workspace for the same checkout are confirmed absent. If any proof is missing, doctor still observes what the failed launch left behind and names the retreat or removal commands for it — close the workspace, remove the retained checkout, or re-add the request when nothing remains — instead of ending at a bare manual-review note. The same observation and commands cover journals already released as `never_launched`. A requeued Worker opens the exact retained abandoned checkout in a fresh workspace instead of trying to create a duplicate linked worktree. Herdr-specific code remains behind runner/automation boundaries so future runners can be added without changing GitHub Issue / PR state semantics.

## Automation hosts

deadloop loads under the pi host and the omp (Oh My Pi) host with no host-specific branch. Module format is declared by file extension — `.cts` for the CommonJS runtime modules, `.ts` for ESM — and `test/module-format-portability.test.ts` fails if a `.ts` file under `src/` or `extensions/deadloop/` assigns `module.exports` or `exports.<name>`.

When running directly from this source checkout, omp discovers the extension through
`.omp/settings.json`. The package manifest remains the installed-package entry point for
both hosts. Keep the project setting pointed at the same `extensions/deadloop/index.ts`
entry so explicit `-e` report checks and normal interactive startup cannot load different
implementations.

Report acceptance on either host, from the primary checkout:

```bash
omp -p -e extensions/deadloop/index.ts "/deadloop-status"
omp -p -e extensions/deadloop/index.ts "/deadloop-doctor"
pi -p -e extensions/deadloop/index.ts "/deadloop-status"
pi -p -e extensions/deadloop/index.ts "/deadloop-doctor"
```

Those report runs never start the scheduler: the `session_start` hook returns early in print and json mode. `/deadloop-enable` starts it in any mode. To accept the scheduler, start the host interactively in an enabled checkout: it takes `~/.pi/agent/deadloop/scheduler.<repository-id hash>.lock` with its own pid at startup, then rewrites `~/.pi/agent/deadloop/state.json` on a startup tick three seconds later and on a 30-second interval anchored to the same startup.

Known host differences: none in the reports or in scheduler behavior. The scheduler lock is scoped to the GitHub repository ID and is host-agnostic, so starting a second host of either kind on the same repository leaves the first one driving and shows `skipped: repository is already served by Automation host pid <pid>` on the second.

The host contract the scheduler relies on is small: `pi.exec` for drivers and `ctx.ui.setStatus` / `ctx.ui.notify` for the status line. The only remaining Automation-host message injection is the code-reload request (ADR 0035), which sends the user-level `/deadloop-reload` command to its own session. To re-verify after a host upgrade without touching GitHub, load a throwaway extension that calls `pi.exec` and the status APIs from `session_start`; a host that cannot run a driver process or report status would leave the loop silent while `state.json` still records ticks.

The automation host and the launched agent are separate choices. `workerAgent` and `reviewerAgent` accept `pi`, `claude`, or `omp`, whichever host runs the automations; the launcher passes the kind straight to `herdr agent start --kind`, which supports all three. `omp` has no session identity flag, so its argv carries only `--thinking`, an optional `--model`, `--auto-approve`, and the `@<prompt file>` reference — Herdr's own `agent start <name>` supplies the attempt name. See ADR 0004 for why a profile may omit the identity flag.
